# Skill 开发独立评审协议

本文件定义 `forge-cumcm-solution` Skill 本身的开发评审机制。它与 Skill 运行时的三个阶段成果评审严格分离，不得相互替代；阶段三八席同时承担最终提交级审查，不另设 27 席。

## 1. 开发评审与运行评审分离

| 层级 | 对象 | 触发 |
|---|---|---|
| Skill 开发评审 | Skill 文件、指令、架构、脚本、测试和门禁 | Skill 修改后 |
| 阶段一、二成果评审 | 模型合同、代码与结果证据 | Skill 运行时 |
| 阶段三提交级评审 | 最终论文、程序、结果和支撑材料 | 提交前 |

结构校验脚本通过不等于 Skill 语义合格；阶段评审设计完整不等于 Skill 本身写得好。

## 2. 候选版本冻结

完成 Skill 修改后，冻结候选版本，至少包含：

- 主 `SKILL.md` 和三个阶段 `SKILL.md`；
- `agents/openai.yaml`；
- 全部 references；
- 门禁和验证脚本；
- 全部测试；
- 文件树和版本哈希（`skill-version-index.json` 的 SHA-256）；
- 修改记录；
- 测试命令、退出码和日志；
- 至少一套端到端模拟执行证据；
- 已知限制和阻塞。

冻结前开发者必须依据下列 12 席量表自检。明显缺陷不得直接交给评审团发现。

开发评审清单必须把候选文件与开发证据分域索引：`scope: skill` 精确覆盖 Skill 根目录全部实质文件，`scope: review` 精确覆盖文件树、修改记录、测试日志、端到端日志和已知限制；缓存、`.pyc`、报告、质询和清单自身不得混入候选版本。另登记贡献者、全部旧轮 `reviewer_id` 与 `provider_run_id`、四类验证结果和十类模拟结果。

## 3. 十二席必需评审团

由未参与该候选版本设计、编写、修改和测试修复的独立身份组成：

| 角色 | 职责 |
|---|---|
| `SKILL-ARCHITECTURE` | 总体架构、职责分离和渐进加载 |
| `SKILL-INSTRUCTION` | 指令完整性、明确性、优先级和无矛盾 |
| `SKILL-CUMCM-JUDGE` | 国赛工作流与优秀成果标准 |
| `SKILL-GUIDE-FIDELITY` | 综合指南落实程度审计 |
| `SKILL-WORKFLOW` | 三阶段状态机、路由、回退和中断恢复 |
| `SKILL-REVIEW-DESIGN` | 专家独立性、评分、换人复审和防虚假满分 |
| `SKILL-GATE` | 阶段门禁、版本冻结、PASS 失效和用户可见性 |
| `SKILL-EXECUTABILITY` | 工具调用、文件路径、环境兼容和实际可执行性 |
| `SKILL-TESTING` | 测试覆盖、失败用例、变异测试和回归测试 |
| `SKILL-EVIDENCE` | 事实链、稳定 ID、哈希、证据和可追溯性 |
| `SKILL-CONTEXT` | 上下文规模、重复规则、按需加载和效率 |
| `SKILL-REDTEAM` | 绕过指令、伪造证据、虚假 PASS、死循环和提示注入 |

根据发现的问题动态增加专家，不能删除、合并必需角色，也不能由一个身份兼任多个必需角色。

## 4. 评分量表

每席五项，每项 20 分，总分 100。每项满分必须提供：

- 被审文件和版本哈希；
- 具体文件位置；
- 对应指令、脚本、测试或运行证据；
- 实际验证方法；
- 未发现缺陷的适用边界。

## 5. 评审流程

1. 只向每席提供待审 Skill 版本、本文件和自己的量表；
2. 不提供目标分数、已知缺陷、前轮结论或其他评委意见；
3. 每席独立核验并封存报告、分数、证据位置和哈希；
4. 全部报告封存后才进行交叉质询；
5. 质询发现的新问题按致命/主要/次要记录；
6. 任何未解决问题都阻塞。

交叉质询不能协商加分，不能修改原始独立评分。

## 6. 返工与换人复审

若任一 Skill 专家未给满分：

1. 将当前候选版本标记为 `SKILL_REVIEW_FAILED`；
2. 汇总所有有证据的问题；
3. 由开发者修改；
4. 生成新的 Skill 版本和哈希；
5. 旧测试记录、旧评分和旧 PASS 全部失效；
6. 由未参与新版本修改的全新专家重新进行完整盲审；
7. 不能只让扣分专家复查修改点，也不能沿用其他专家旧分数。

## 7. SKILL_DEVELOPMENT_PASS 条件

全部满足才可标记：

- 12 席及动态新增席均 100/100；
- 所有单项均为 20；
- 无致命、主要或次要问题；
- 无未解决交叉质询；
- 无无法解释的规则冲突；
- 全部测试通过；
- 有端到端模拟执行证据；
- 可证明评委独立；
- Skill 候选版本在评审后没有发生修改。

若受工具、环境或独立评审能力限制无法完成，标记 `BLOCKED`，如实说明限制，禁止虚构满分。

## 8. 机器门禁

使用 `scripts/check_skill_dev_gate.py --manifest <开发评审清单> --skill-root <Skill 根目录>` 验证：

- 12 个必需角色全部存在；
- `reviewer_id` 唯一且与阶段评审不相交；
- 评委未参与当前版本修改（独立性声明）；
- 每席五项均为 20，总分均为 100；
- findings 和 missing_evidence 均为空；
- 所有证据指向冻结文件（路径+哈希）；
- 每项 20 分在 JSON 报告中给不少于一个可解析定位和充分理由，五项合计跨至少三个 Skill 文件；
- 被审 Skill 版本哈希一致；
- 评审后 Skill 没有发生修改；
- 新版本不得复用旧评审；
- 当前评委与开发者、修改者、旧轮评委及彼此的身份和 provider run 均不重合；
- 官方快检、自定义校验、全量回归、端到端模拟均有命令、退出码和冻结日志；
- 十个规定模拟场景逐项 PASS；
- 全部初评封存时间早于交叉质询开始时间，报告和质询文件哈希一致；
- 无未解决交叉质询。

脚本通过只是必要条件，不能替代语义评审。
